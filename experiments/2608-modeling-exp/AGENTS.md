# 2608-modeling-exp 작업 규칙

이 디렉터리는 저장소의 다른 실험과 **다른 스타일 계약**을 따른다. 이 파일은 이
디렉터리 안에서 작업할 때 최상위 `AGENTS.md`보다 우선한다.

## 목적

`experiments/2607-notion-energy-vmp/src/google2019_toy/build_toy_instance.py`
(4,283줄, 함수 58개)의 전처리를 **사람이 한 줄씩 읽고 검수할 수 있는 코드**로
다시 쓴다. 최종 독자는 이 저장소의 연구자 본인이며, 목표는 "동작하는 코드"가
아니라 "저자가 전처리의 모든 결정을 직접 이해한 상태"다.

따라서 읽기 쉬움은 부차적 품질 항목이 아니라 **1순위 요구사항**이다. 정확하지만
읽기 어려운 코드는 이 디렉터리에서 실패한 코드다.

## 2607 스타일을 따르지 말 것

2607 코드에는 SHA-256 재검증, 1e-12/1e-5 이중 허용오차, atomic publish 계약,
no-incumbent 분리 경로 같은 감사 우선 규율이 있다. 연구 재현성 목적에는 맞지만
이 디렉터리의 목적에는 정반대다. **주변 코드에서 스타일을 추론하지 말고 아래
규칙을 따른다.**

## 필수 규칙

1. **단계당 파일 하나.** 파일 이름은 `s<번호>_<이름>.py`. 한 파일은 파이프라인의
   한 단계만 담당한다.
2. **함수는 40줄 이하.** 초과하면 단계를 잘못 쪼갠 것이다. 파일당 함수 8개 이하.

3. **한 줄은 100자 이하.** 줄 수 상한을 긴 줄로 우회하지 말 것. 여러 문장을 한
   줄에 밀어넣거나 긴 컬럼 목록을 한 줄에 늘어놓아서 함수를 40줄 안에 맞췄다면
   규칙 2를 지킨 것이 아니라 어긴 것이다. 두 상한은 함께 지켜야 의미가 있다.
3. **모든 단계는 중간 산출물을 디스크에 남긴다.** 다음 단계는 앞 단계의 파일을
   읽어서 시작한다. 사람이 각 단계 출력을 따로 열어볼 수 있어야 한다.
4. **단계 하나는 단독 실행 가능해야 한다.** `python s3_episodes.py` 만으로 그
   단계를 재현할 수 있어야 하고, 앞 단계를 다시 돌릴 필요가 없어야 한다.
5. **순수 함수 + 얇은 `main()`.** 변환 로직은 DataFrame을 받아 DataFrame을 반환
   한다. 파일 입출력은 `main()`에만 둔다.
6. **중간 변수에 이름을 붙인다.** pandas 체이닝은 3단계 이하. 이름 없는 중간
   결과가 길게 이어지면 검수가 불가능하다.
7. **모든 함수에 한 줄 docstring.** 정확히 한 문장이고 한 줄을 넘기지 않는다.
   그 함수가 무엇을 반환하는지를 쓴다. `Args:` / `Returns:` / `Raises:` 같은
   섹션은 **금지**한다 — 타입 힌트에 이미 있는 정보를 반복하지 않는다.

   ```python
   def _joint_shape_weights(intervals: pd.DataFrame) -> pd.DataFrame:
       """(cpu, mem) 용량 쌍별 active duration 합계를 반환한다."""
   ```

8. **파일 상단에 모듈 docstring.** 3줄 이내로 이 단계의 입력 → 출력과 존재
   이유를 쓴다. 단계 스크립트에는 검증 수치도 한 줄 넣는다.

9. **인라인 주석은 "왜"만 쓴다.** 코드가 무엇을 하는지는 코드로 보이게 하고,
   코드만 봐서는 알 수 없는 것에만 주석을 단다. 대표적으로 trace의 결함에
   대응하는 자리와, 달리 짜도 될 것 같지만 그러면 결과 숫자가 바뀌는 자리다.

   양쪽 다 실패다 — 주석이 없어서 왜 이렇게 짰는지 알 수 없는 코드도, 코드를
   그대로 한국어로 옮긴 주석이 줄마다 붙은 코드도 반려한다. 판단은 작성자가
   하되, 어느 쪽으로 치우쳤는지는 리뷰에서 지적한다.

10. **용어는 [DATA_GLOSSARY.md](./DATA_GLOSSARY.md)를 따른다.** 변수명과 주석에
    쓰는 데이터 용어는 용어집에 있는 것을 쓴다. 용어집에 없는 개념을 새로
    도입해야 하면 코드보다 먼저 용어집에 한 항목을 추가한다. 독자가 모르는
    명사가 나오는 코드는 검수할 수 없다.

## 금지 규칙

1. **방어적 감사 계층 금지.** 결과 숫자를 바꾸지 않는 검증·감사·진단 코드를
   파이프라인에 넣지 않는다. 2607의 `audit_assigned_machine_cpu_capacity`(393줄),
   `_write_scaling_diagnostics`, `_write_preprocessing_diagnostics`,
   `_write_metadata`에 해당하는 코드는 **이식하지 않는다.**
2. **진단 JSON 생성 금지.** `preprocessing_diagnostics.json`,
   `scaling_diagnostics.json`은 만들지 않는다.
3. **컬럼명 fallback 금지.** `_first_existing(df, ["a", "b", "c"])` 처럼 여러
   이름을 시도하는 코드를 쓰지 않는다. 입력 스키마는 하나로 고정하고, 없으면
   그냥 `KeyError`가 나게 둔다.
4. **하위호환 분기 금지.** `strict_event_state=True/False` 처럼 한쪽만 쓰는
   플래그를 만들지 않는다. 실제로 쓰는 경로만 구현한다.
5. **조기 추상화 금지.** 두 번 이상 실제로 반복되기 전에는 헬퍼로 빼지 않는다.
   한 곳에서만 쓰이는 3줄 헬퍼는 호출 지점에 인라인한다.
6. **방어적 예외 처리 금지.** 입력이 계약을 어기면 그냥 죽게 둔다. `try/except`로
   감싸서 기본값으로 진행하지 않는다.
7. **검증 코드를 파이프라인에 섞지 말 것.** 기존 데이터와의 비교는 `verify_*.py`
   에 분리한다. 파이프라인 파일에는 assert를 두지 않는다.

## 수치 정합성

현 단계에서는 산출물이 기존 canonical 데이터셋
`data/processed/notion_toy_google2019_v5_mode_capacity_bounded`와 **수치적으로
일치해야 한다.** 일치 자체가 목적이 아니라, 일치가 곧 "기존 4,283줄이 실제로
무엇을 하고 있었는지 정확히 이해했다"는 증거이기 때문이다.

단, 여기에는 상한이 있다: **일치에 기여하지 않는 코드는 쓰지 않는다.** 기존
코드의 상당 부분은 결과 숫자에 영향을 주지 않는 감사·진단이다. 그 부분은
재현 대상이 아니다. 판단 기준은 하나다 — "이 코드를 지우면 출력 숫자가
바뀌는가?" 바뀌지 않으면 쓰지 않는다.

정합성 요구는 검수 이후 완화될 예정이다. 저자가 각 로직을 읽고 불필요하다고
판단한 것을 직접 제거할 것이므로, **제거하기 쉬운 형태로** 써야 한다. 즉 trace
결함 대응 로직은 한 함수에 모아 두고, 지웠을 때 어디가 깨지는지 명확해야 한다.
