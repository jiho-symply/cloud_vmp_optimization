# Workload Classes: On-Demand, Spot/Preemptible, and Batch/Deferable

## Claim

On-demand, spot/preemptible, and batch/deferable workloads are realistic abstractions if they are interpreted as service-level and recourse classes, not as a complete taxonomy of cloud products. The core distinction is operational: some demand is protected and should be served with high probability, some demand accepts provider- or scheduler-initiated interruption in exchange for lower cost or lower priority, and some work is submitted to a managed batch service that can decide when and where to allocate VM capacity or server-time before a deadline.

This abstraction should be presented as model-centric. It is not tied to any one trace, cloud vendor, or CPU-only dataset. The strongest claim is that large cloud and cluster systems routinely differentiate workloads by priority, revocability, delay tolerance, reservation, and recovery mechanism. The weaker claim, which should be avoided, is that all real workloads naturally fall into exactly these three mutually exclusive classes.

For this document, "batch" should be read in the managed-batch sense: a provider-facing or platform-facing service accepts delay-tolerant jobs, plans capacity over time, reserves or allocates compute slots, and processes the submitted work before a completion target. It is not merely a label in a trace, and it is not the same thing as spot capacity. Batch is a workload/service property; spot/preemptible is a capacity contract or priority property.

## How the Current Model Matches

The current model maps the three classes to different feasibility and recourse rules:

- On-demand VMs are the protected class. Variables $x_{is}$, $x^R_{ist}(\xi)$, $m_{it}(\xi)$, $\phi_{st}(\xi)$, and $\eta_s(\xi)$ encode initial placement, scenario-time placement, limited migration, and service-risk accounting. This is consistent with a class whose violation is expensive and should be controlled by chance, CVaR, or robust constraints. The class should be described as high-priority protected demand, not necessarily as a literal public-cloud billing SKU.
- Spot/preemptible VMs are the revocable lower-priority class. Variables $y_{js}$, $y^R_{jst}(\xi)$, $\gamma_{st}(\xi)$, and $\delta_j(\xi)$ encode baseline placement and scenario-dependent suspension or curtailment. This captures the key modeling property of transient capacity: the platform may interrupt, curtail, or defer it when capacity is scarce. The model abstracts away market prices, bids, warning times, and checkpoint state.
- Managed batch jobs are the time-flexible work class. Variables $b_{kst}$ and $z_{kst}(\xi)$ model reserved server-time slots and realized processed volume. This fits a provider-managed batch abstraction where the platform accepts a delay-tolerant job, reserves or allocates VM capacity in advance, and then consumes that reserved server-time to process work over the planning horizon. Completion over a horizon matters more than uninterrupted execution at a fixed instant.

The separation is useful because each class has a different penalty surface: protected-demand overload, spot/preemptible suspension, and managed-batch under-processing are not operationally equivalent. The model's scenario probabilities then express uncertainty in demand, resource usage, and available capacity without requiring the evidence to come from a specific vendor trace.

## Different Modeling Choices in the Literature

The literature supports the three-class abstraction, but it implements the distinctions in several different ways:

- Contract-based classes: SpotOn and SpotCheck distinguish fixed-price, non-revocable on-demand resources from cheaper revocable spot resources. Models in this family often include prices, bids, market selection, revocation probabilities, checkpointing, migration, or replication. This is the closest evidence for the on-demand versus spot distinction, but it is richer than the current suspension-only model.
- Priority-based cluster classes: Borg and later Borg trace work distinguish production, best-effort, and batch-like work through priority, quota, admission control, and over-commitment rather than public-cloud instance contracts. This is closer to an internal scheduler view, where on-demand means high-priority protected service rather than a billing product.
- Reservation-based batch services: Rayon models future resource reservations for production and best-effort big-data jobs. This is the closest evidence for the model's managed-batch reservation variables: $b_{kst}$ can be interpreted as planned server-time allocated to accepted delay-tolerant jobs. A richer batch-service model would include admission decisions, job queues, deadlines, and possibly a reservation language.
- Prediction-based classes: Resource Central uses workload telemetry and learned predictions to guide placement and oversubscription. This suggests an alternative to fixed exogenous classes: infer class behavior from historical lifetime, deployment size, production tag, utilization, and risk tolerance.
- Batch workflow and bag-of-jobs classes: SciSpot models scientific workloads as bags of jobs and uses preemption-aware server selection. Other batch models may require integer task completion, deadlines, precedence constraints, data locality, queueing policies, or checkpoint intervals rather than continuous processed volume.
- Overlapping classes: Batch work can run on on-demand instances, spot instances, or best-effort internal tiers. Spot/preemptible is a resource contract or availability property, while batch/deferable is a workload/service property. The current model separates them for tractability, but real systems often combine them.
- Richer recourse: The current model uses migration for on-demand VMs, suspension for spot VMs, and continuous processing for batch jobs. The cited spot/preemptible systems show other valid recourse choices, including checkpoint/restart, live migration, replication, fallback to on-demand instances, portfolio selection, and market switching.

## Caveats

The abstraction is realistic only at the level of scheduling roles. It should not be described as an exhaustive ontology of cloud workloads. Reserved instances, savings-plan capacity, serverless jobs, interactive analytics, streaming systems, GPU training, storage-heavy services, and network-sensitive services may need additional classes or dimensions.

Spot/preemptible and batch/deferable are orthogonal concepts. A workload can be batch but run on protected on-demand capacity, or it can be a long-running service deployed on transient resources with replication. The current formulation intentionally separates them so that risk-aware placement tradeoffs remain readable.

The managed-batch model is a fluid or divisible approximation. Many real batch services schedule indivisible tasks with release times, deadlines, dependencies, setup times, checkpoint costs, failure retries, and data-locality constraints. The continuous variable $z_{kst}(\xi)$ is best framed as a planning relaxation, an aggregate model for many small independent tasks, or a server-time accounting model for accepted batch demand.

The spot model uses suspension as the low-priority recourse. That captures the service-level effect of interruption, but it omits the richer mechanisms found in SpotOn, SpotCheck, and SciSpot. A stronger spot model could include revocation-time distributions, warning times, checkpoint state, restart costs, replicated execution, fallback to protected capacity, or provider-specific maximum lifetimes.

Resource contention can be used as an SLA-risk proxy, but it is not a complete SLA model. The cited systems distinguish production, best-effort, and batch work partly because contention affects latency, progress, and failure recovery differently. If the paper claims SLA compliance, it should specify whether the SLA event is resource-capacity overflow, queueing delay, missed batch completion, tenant-level slowdown, or a direct latency/availability target.

The workload-class argument is independent of the scalar CPU-capacity simplification. Class realism does not imply that CPU-only placement is production-complete; a production scheduler would usually require at least CPU and memory, and often network, storage, accelerator, locality, and failure-domain constraints.

## Verdict

The three classes are defensible as a compact research abstraction for stochastic temporal VM placement. Peer-reviewed cluster and cloud systems literature supports separating protected demand, revocable or low-priority demand, and managed delay-tolerant batch work because these roles have different service expectations, reservation needs, and recourse mechanisms.

The current model should therefore claim realism in a limited sense: it captures an important operational pattern for risk-aware consolidation and temporal placement. It should not claim that on-demand, spot/preemptible, and managed batch are universal, mutually exclusive, or sufficient for a production-grade cloud scheduler without additional resource dimensions, richer recourse, and explicit job-level semantics.
