# Temporal Bin Packing and Virtual Machine Placement

## Claim

Virtual machine placement maps naturally to temporal bin packing when the operational question is: assign workloads with time-dependent residency or processing windows to capacitated servers while using as few server resources as possible and preserving service risk limits. In that abstraction, VMs, low-priority instances, and reserved batch work are items or work volumes; physical servers are bins; resource capacity is enforced over time; and server activation/fire-up decisions represent the economic and energy cost of keeping capacity available.

This is not an Azure-specific claim. It is a modeling claim about cloud and server-consolidation operations: demand varies over time, idle or frequently restarted servers have operational consequences, and realized workload can differ from nominal reservations. The current model is therefore best justified as a stochastic temporal VMP/TBPP prototype with recourse, not as a complete production scheduler.

## How the Current Model Matches

The current first-stage variables match the deterministic core of temporal bin packing. Using the notation in `09_notation_and_terms.md`, $x_{is}$ and $y_{js}$ assign VMs to servers, $b_{kst}$ reserves server-time processing slots, and $u_{st}$/$u_s$ decide whether a server is powered or used over the planning horizon. This corresponds to the TBPP view in which an item consumes bin capacity only during its active time window, and capacity must hold at every relevant time instant.

The model also matches the fire-up/activation extension of TBPP. The literature distinguishes minimizing the number of servers used from minimizing the number of server starts or idle periods, because both the amount of capacity online and the switching pattern affect energy and service quality. The current $u_{st}$ variables are closer to time-indexed activation than to a pure startup count, but they are the right state variables from which active-server cost, active-server-time cost, and explicit startup variables can be built.

The second stage extends deterministic temporal bin packing into stochastic operations. Scenario-indexed variables $x^R_{ist}(\xi)$, $y^R_{jst}(\xi)$, and $z_{kst}(\xi)$ let the plan react to realized demand through migration, suspension/curtailment, and batch processing decisions. The overload and suspension indicators $\phi_{st}(\xi)$, $\eta_s(\xi)$, $\gamma_{st}(\xi)$, and $\delta_j(\xi)$ turn service outcomes into chance-style or CVaR-style risk controls. This is consistent with stochastic and chance-constrained bin-packing work, where uncertain item sizes or realized usage require probabilistic capacity guarantees rather than deterministic packing of nominal sizes.

The scalar CPU abstraction is a defensible narrow version of this mapping. Several temporal and stochastic bin-packing papers use a single resource to isolate the core combinatorial structure, and Aydin et al. explicitly note the common modeling move of using one binding resource. For general-purpose production VMP, however, multi-resource and heterogeneous-server formulations are stronger operational models.

Recent work after the original cloud-oriented TBPP papers strengthens this mapping. Newer EJOR, INFORMS Journal on Optimization, Annals of Operations Research, and 4OR papers continue to study TBPP, TBPP with fire-ups, busy-time minimization, and half-capacity cloud-style cases. These papers do not match the current stochastic recourse model exactly, but they show that the time-windowed jobs-to-servers abstraction is still an active and credible OR modeling line for cloud and data-center workload management.

The exact intersection of "temporal bin packing for VM placement" and "stochastic VM resource usage" is still sparse. The best-supported argument is therefore a bridge: deterministic TBPP/VMP papers justify the time-windowed placement skeleton, stochastic bin-packing and risk-aware overbooking papers justify replacing fixed item sizes with random or time-varying VM resource usage, and production VM allocation papers justify using lifetime/load predictions in dynamic packing. This bridge is directly aligned with the current model's scenario-indexed loads and chance/CVaR-style capacity-risk controls.

The paper should therefore cite evidence in tiers. Aydin et al., Dell'Amico et al., Martinovic et al., and Muir et al. support temporal packing and server activation. Hong et al., Yan et al., Martinovic and Selch, Martinovic et al. TOP, Zhang et al., and Cohen et al. support stochastic or chance-constrained packing. Buchbinder et al. and Barbalho et al. support dynamic VM allocation with predicted lifetime/load. None of these papers alone justifies the full current combination of on-demand migration, spot suspension, Managed Batch reservation, 24-hour two-stage scenarios, and scalar CPU capacity.

## Different Modeling Choices in the Literature

The simplest TBPP choice is deterministic fixed-window placement: each item has a known size and lifetime, is assigned once, and capacity is checked over time. Dell'Amico et al. use this form to study exact formulations and branch-and-price.

Before the TBPP terminology became common in the OR literature, server-consolidation papers already used a closely related temporal VMP idea. Speitkamp and Bichler model VM/server consolidation with workload logs and daily cycles, while Setzer and Bichler assign VMs to physical servers under per-time resource constraints derived from cyclic time-series data. Post-2017 systems papers strengthen this line: Buchbinder et al. model online VM allocation as dynamic bin packing with lifetime and load predictions, and Barbalho et al. describe production VM allocation in Microsoft Azure as multi-dimensional dynamic bin packing with lifetime predictions. These papers are useful because they show why time-varying VM usage, VM lifetime, and workload forecasts should enter placement constraints, even though they do not use stochastic recourse.

A second choice adds activation/fire-up structure. Aydin et al. and Martinovic et al. separate the number of servers used from the number of times servers are switched on, because minimizing active servers alone does not necessarily minimize switching events. The current model's $u_{st}$ can support either active-server-time costs or an explicit startup extension such as $q_{st} \ge u_{st}-u_{s,t-1}$.

A third choice minimizes active-bin time rather than only bin count or fire-up count. Muir et al. and Martinovic and Strasdat's busy-time work support the current energy objective's interpretation as a powered-server-time proxy. This is close to the current $\sum_{s,t}u_{st}$ term, whereas fire-up minimization would require transition variables.

A fourth choice makes item sizes stochastic or time-varying. Martinovic and Selch model uncertain item sizes with chance-style capacity feasibility, Martinovic et al. model stochastic server consolidation with conflicts, Zhang et al. provide a two-stage stochastic/chance-constrained bin-packing formulation, and Hong et al. study stochastic bin packing with time-varying item sizes motivated by VM scheduling. In cloud-specific work, Wang et al., Breitgand and Epstein, Hwang and Pedram, Yu et al., Zhou et al., Chen et al., Yan et al., and Cohen et al. all support the core premise that VM or container resource usage can be random, bursty, correlated, dynamic, or risk-controlled rather than a fixed deterministic reservation. The current scenario model is more operationally detailed than a single chance-constrained bin-packing row because it also chooses migration, suspension, and batch-processing recourse.

A fifth choice is multi-resource, heterogeneous, or topology-constrained VMP. Meroni and Guitart emphasize distinct capacities, power consumption, performance profiles, and migration costs. Borisovsky et al. and Turnaev and Panin show recent TBPP extensions toward placement groups, rack/failure-domain structure, and VM-specific constraints. Those features are important for production placement, while the current scalar CPU model is a deliberate prototype abstraction.

A sixth choice is online or rolling reoptimization. Bobroff et al. support the operational value of revising placement as workload forecasts change. The current two-stage model captures a planning-plus-recourse version of that idea, but it is not a full online scheduler.

## Caveats

The TBPP mapping is strongest when workload intervals or planning slots are known or forecastable. If arrivals are purely online, if migration duration dominates the control interval, or if network and storage topology constraints are first-order effects, a richer VMP model is needed.

Server activation is not identical to fire-up count. Penalizing $u_{st}$ captures powered-server-time; penalizing transitions captures startup frequency. If startup wear, boot latency, or cold-start energy is central, explicit startup variables should be added rather than inferred only from server-active states.

The current CPU-only capacity is a narrow but common modeling cut. It should be described as suitable for CPU-dominant workloads or for isolating stochastic temporal consolidation behavior, not as a general cloud placement model. Memory, network, storage, accelerator, interference, affinity, and fault-domain constraints remain outside this topic file's justification.

Batch processing through continuous $z_{kst}(\xi)$ is adjacent to, but not identical with, classical TBPP item placement. It is better described as reserving server-time capacity for divisible work, layered on top of the temporal bin-packing placement model.

## Verdict

The current model is well justified as a stochastic temporal VMP/TBPP research abstraction. The deterministic TBPP literature supports the time-windowed packing core, the TBPP-FU literature supports server activation and fire-up objectives, and stochastic/chance-constrained bin-packing work supports probabilistic overload controls. The strongest defensible claim is that this model captures the main operations tradeoff among consolidation, activation, migration, low-priority degradation, and service-risk control. It should not be presented as a complete production-grade VMP scheduler without the caveats above.
