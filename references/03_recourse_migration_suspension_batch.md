# Recourse as Migration, Spot Preemption/Suspension, and Managed Batch Processing

## Claim

The current recourse design is defensible as a placement-level operations model if its controls are interpreted narrowly:

- protected on-demand VMs may be re-placed through migration, but migration must be costly and capacity-constrained rather than free;
- spot/preemptible VMs may be curtailed as revocable lower-priority work, but realistic "suspension" requires explicit preemption or revocation decisions, capacity reclamation, checkpoint/restart or migration cost, warning or remaining-lifetime semantics when the cloud contract provides them, and accounting for lost service or lost work;
- Managed Batch style workload is plausible when the provider accepts delay-tolerant jobs, reserves VM capacity or server-time for aggregate batch processing, and then processes a divisible workload or a large pool of independent tasks over time.

The claim should stay limited. The model captures recourse decisions at the placement and capacity-allocation level. It does not fully model live-migration protocols, public spot-market bidding, guest memory checkpointing, hibernation state, restart placement, or integer task scheduling. The model is strongest as a compact stochastic optimization abstraction for studying service priority, capacity reclamation, and consolidation tradeoffs under uncertain demand.

## How the Current Model Matches

The first stage commits to baseline placements and reserved processing:

- $x_{is}$ assigns each on-demand VM to an initial server.
- $y_{js}$ assigns each spot/preemptible VM to a baseline server.
- $b_{kst}$ reserves server-time slots for Managed Batch processing.

The second stage reacts to a realized scenario:

- $x^R_{ist}(\xi)$ represents the realized server of an active on-demand VM after recourse.
- $m_{it}(\xi)$ prices and limits migration events when an on-demand VM changes server between active periods.
- $y^R_{jst}(\xi)$ represents whether a spot/preemptible VM remains served at a server-time point after low-priority curtailment.
- $z_{kst}(\xi)$ is continuous batch volume processed on reserved or available capacity.
- $\phi_{st}(\xi)$, $\eta_s(\xi)$, $\gamma_{st}(\xi)$, and $\delta_j(\xi)$ separate high-priority overload/SLA loss from lower-priority suspension, lost-work, or unprocessed-batch penalties.

This hierarchy matches production operations only if the semantics are made precise. For on-demand VMs, $m_{it}(\xi)$ should mean that migration is available but consumes time, network, memory, and/or a penalty budget. For spot VMs, $y^R_{jst}(\xi)=0$ should not be described as effortless suspension unless the model includes state preservation. The safer interpretation is "revocable service is not provided in that period." If the paper wants to claim realistic spot suspension, the placement model should add or explicitly discuss the following elements:

- a revocation/preemption variable such as $p_{jt}(\xi)$ that records a transition from served to unserved state;
- a capacity reclamation constraint showing that preempted or suspended spot VMs release CPU, memory, and any other modeled resource at the relevant time;
- checkpoint, restart, hibernation, or migration variables/costs, because spot systems usually tolerate revocation through checkpointing, replication, restart, or migration rather than by simply disappearing from the placement;
- warning-window or remaining-lifetime parameters where applicable, for example a notice period before revocation or a time-dependent preemption hazard for temporally constrained preemptible VMs;
- service-loss accounting, such as lost spot runtime, lost progress since the last checkpoint, restart delay, degraded availability, or lower-priority SLA credit.

The Managed Batch interpretation should also be explicit. $b_{kst}$ is best read as first-stage reservation of VM capacity or server-time for a managed batch service, not as a guarantee that a particular indivisible job is bound to a particular server. $z_{kst}(\xi)$ is then a second-stage processing decision for aggregate backlog. This is appropriate for a public-cloud batch service that receives many independent tasks, parameter sweeps, data-parallel tasks, or divisible work units. If each batch job is indivisible, has precedence constraints, has large local state, or must complete as an exact task schedule, $z_{kst}(\xi)$ should be replaced or supplemented by integer task variables, release times, deadlines, and checkpoint state.

## Different Modeling Choices in the Literature

Migration is often modeled at protocol level. Migration surveys describe pre-copy, post-copy, hybrid migration, migration time, downtime, dirty-page rate, transferred bytes, and source/destination resource overlap. The current model instead treats migration as a scenario-specific placement change with a binary event cost and an at-most-one-migration style control. That abstraction is appropriate for a high-level recourse study, but it should not be used to compare migration protocols or claim negligible migration disruption.

Spot and preemptible resources are modeled in several distinct ways. SpotOn and SpotCheck focus on public spot-market risk and customer-side mechanisms such as checkpointing, migration, replication, and restore. SciSpot focuses on temporally constrained preemption risk and remaining lifetime for preemptible VMs. Resource Deflation and Cloud-scale VM Deflation model provider-side resource reclamation from transient VMs, where low-priority resources may be shrunk instead of fully preempted. Borg models priority-driven cluster sharing and rescheduling of lower-priority work. The current model is closest to a provider-side priority-capacity abstraction, but it should use the word "suspension" only when state preservation, restart, or hibernation semantics are represented. Otherwise, "preemption," "revocation," or "curtailment" is more accurate.

Managed Batch can be modeled at task level or fluid level. Task-level systems such as Borg, Apollo, and TR-Spark represent jobs as many tasks, scheduling decisions, recovery mechanisms, and runtime-dependent behavior. Divisible-load models represent work as splittable processing volume. The current $z_{kst}(\xi)$ variable follows the fluid/aggregate style: it is a throughput and backlog abstraction for many similar units of work, not an exact execution trace for each batch task.

SLA accounting also differs across papers. For protected on-demand VMs, resource contention or overload can reasonably proxy SLA risk, although migration downtime and performance degradation should also be charged if migration is frequent. For spot/preemptible VMs, the more natural loss metrics are revocation events, unserved VM-time, lost progress, checkpoint overhead, restart delay, and lower-priority service credits. For Managed Batch, the natural loss metrics are unfinished backlog, deadline misses, makespan, flow time, or tardiness. Therefore a single resource-contention SLA metric is too narrow if the model claims to evaluate all three workload classes.

## Caveats

On-demand migration is not free. The model's $m_{it}(\xi)$ variable can penalize recourse, but it does not reserve migration bandwidth, model migration duration, protect destination memory, or represent downtime. It is best interpreted as "migration is available but costly and limited," not as "migration is instantaneous."

Spot/preemptible suspension should be interpreted carefully. In public clouds, customers usually handle provider revocation through checkpointing, replication, restart, migration, or application-level fault tolerance. In a provider-side placement model, it is reasonable to let low-priority or revocable work absorb scarcity, but a realistic formulation should include preemption variables, reclaimed capacity, checkpoint/restart or migration cost, warning or lifetime semantics when applicable, and service-loss accounting. Arbitrary stateful spot VMs should not be assumed suspendable without explicit state cost.

Managed Batch reservation is plausible as server-time reservation for a managed service, not as a guarantee that a specific indivisible job runs on a fixed server. The fluid batch variable is strong for divisible data processing, large pools of independent tasks, parameter sweeps, and aggregate backlog. It is weak for a single indivisible job, a precedence-constrained workflow, a job with large local state, or deadline-sensitive task scheduling where exact completion time matters.

Production systems usually require multi-resource accounting. Migration and suspension depend heavily on memory, storage state, and network bandwidth, while batch placement depends on CPU, memory, disk, and network needs. A CPU-only model can still support a prototype recourse study, but the paper should present it as a deliberately narrow abstraction.

## Verdict

The recourse abstraction is operationally reasonable for a stochastic temporal VM placement prototype if it is framed as a high-level priority and capacity-reclamation model. It captures three important control levers: migrate protected on-demand service, curtail or reclaim revocable spot capacity, and allocate reserved server-time to aggregate Managed Batch processing.

The strongest wording is conditional. The current formulation justifies "spot curtailment/preemption" more directly than true "spot suspension." To claim realistic suspension, add explicit revocation state, capacity reclamation, checkpoint/restart or migration cost, warning or remaining-lifetime semantics when applicable, and service-loss accounting. For Managed Batch, keep `z` as an aggregate divisible or many-task processing variable, and avoid claiming it models exact task-level schedules unless integer task, deadline, precedence, and state variables are added.
